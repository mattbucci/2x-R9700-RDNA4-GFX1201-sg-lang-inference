### Note — qwen36-moe vision probe (root-caused, not a regression)
The vision probe originally showed a repeated `"answer</think>"` fragment in `content`. Root-caused by
direct probing: the qwen36 chat template injects `<think>\n` by default, so the perception probe forced
qwen36 (a reasoning model) into thinking on a trivial "describe this image" prompt with only a 128-token
cap. With nothing distinct to say after the think block, the decode stochastically degenerates into a
repeated `answer</think>` loop that runs to `max_tokens`; the qwen3 reasoning parser splits on the first
`</think>` and leaks the later markers into `content`. Confirmed it is **not vision-specific** (a trivial
*text* prompt truncates identically at 128 tokens) and **stochastic** (a larger budget doesn't prevent it —
the loop just runs longer; thinking-off is clean every time). It is a reasoning-model/probe interaction,
not a serving defect or a rebase regression — the chat template and parser are unchanged, and qwen36
reasons and answers correctly given an adequate budget.

Fix: `scripts/eval/validate_capabilities.py` now disables thinking for the perception check
(`chat_template_kwargs={"enable_thinking": false}`), which yields a clean, deterministic description on
every run; the separate thinking probe (8192-token budget) still exercises reasoning. qwen36-moe is 4/4
clean after the fix. (Related and distinct: the pre-existing v0.5.15 `qwen3_coder` `<tool_call>` content
leak — a dangling start marker surfacing in `message.content` after a tool result — was separately
investigated and is **resolved on v0.5.16**: the serving auto-path runs the parser and returns the stripped
`normal_text`, so a dangling marker never reaches content. Verified by serving-path replication, 56 clean
live samples, and the streaming path; regression-guarded by
`scripts/eval/test_qwen3coder_dangling_toolcall.py`.)
