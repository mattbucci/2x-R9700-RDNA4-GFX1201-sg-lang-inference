# SGLang v0.5.18 rebase validation

## Target

- SGLang tag: `v0.5.18` (peeled commit `71de97b264b04dcd514cf904003028aefe9775c8`, tagged 2026-08-20)
- Serving tree: `/data/sgl-v0518`  ·  Conda environment: `sglang-triton36-v0518`
- PyTorch `2.11.0+rocm7.2` · Triton `3.6.0` · transformers `5.12.1` (unchanged) · ROCm 7.2.3
- Previous base: v0.5.16 (`fdebc938`). v0.5.17 was skipped; the delta v0.5.16→v0.5.18 is 4513 files,
  +405k/−100k lines.

## Upstream changes that shaped this rebase

- **Kernel tree relocation.** `sgl-kernel/` is gone from the monorepo (removed in v0.5.17). Its source now
  lives at `python/sglang/kernels/aot/` (the `sglang-kernel` 0.4.6.post1 package source, still with
  `setup_rocm.py`). Patches 003/006/008/032 are re-pathed there; `scripts/setup.sh` and the three native
  builders resolve the kernel dir version-aware (`default_sgl_kernel_dir` in `scripts/common.sh`).
- **`sglang.jit_kernel` is gone.** JIT/Triton modules moved under `python/sglang/kernels/ops/...`
  (`moe_fused_gate` → `kernels/ops/moe/`, `triton_store_cache` → `kernels/ops/kvcache/`,
  `minimax_m3/rmsnorm` → `kernels/ops/layernorm/minimax_m3_rmsnorm.py`). `test/registered/jit/` →
  `test/registered/kernels/`. Patches 065/081/082/097 and their tests are re-pathed; 065's
  `tree_verify_attention.py` now lives at `kernels/ops/attention/` next to the kernels it imports.
- **Packaging split.** `python/pyproject.toml` is now the CUDA build (pins `torch==2.13.0`, flashinfer
  cu13, sgl-deep-*, nvidia-*, tilelang, …); `python/pyproject_other.toml` carries the platform-neutral
  `runtime_common` extra used by upstream's ROCm image. `setup.sh` installs the package with `--no-deps`
  and resolves `runtime_common` from `pyproject_other.toml`, adds the ROCm-side extras the CUDA file
  carried (`numba`, `zstandard`, `watchfiles`, `torchcodec==0.11.1` for the torch-2.11 ABI), and installs
  the `sglang-kernel==0.4.6.post1` wheel as the package skeleton for the HIP `common_ops` overlay. The
  `srt_hip` extra's `petit_kernel`/`wave-lang` (MI300 FP4 / wave attention) are deliberately not installed.
- **OCI image.** `Dockerfile` pins `v0.5.18` / `71de97b2`; `docker/build-sglang.sh`'s TP=1 store-cache
  fallback tweak now targets `python/sglang/kernels/ops/kvcache/kvcache.py` (signature-tolerant anchor,
  `can_use_store_cache(k_row_bytes, v_row_bytes=0)`); the sampler guard target is unchanged. Not rebuilt
  as part of this rebase.
- **Runtime context.** `get_server_args()` reads inside layers became `get_exec().comm.*` /
  `get_spec().*`; `ModelRunner.dcp_size` no longer exists (`server_args.dcp_size`); the scheduler's
  `get_internal_state` reads `get_context().resolved_server_args_dict()`.
- **`SGLANG_OPT_USE_JIT_KERNEL_FUSED_TOPK` was removed**; the unified Triton router is unconditional
  on CUDA. Upstream also added a guarded `download_remote_media` (SSRF policy) for HTTP media, a
  `mambaish_config` union for hybrid v-head-dim detection, `ModelConfig.get_max_num_attention_heads()`,
  `is_lm_only`, and a reworked MoE tuner (`enable_up_tma`, three tuning rounds).

## Series transition: 69 → 70

Independent dry-run of the v0.5.16 series on pristine v0.5.18: **37 applied clean, 32 required work.**
Sequential rebase result: **43 unchanged, 26 regenerated** (2 pure re-paths, 8 fuzz-only, 16 hand-rebased).
No patch was dropped; **1 patch added** — `098-gemma4-unified-native-config`: sglang's
`_Gemma4UnifiedConfigAlias` (a `Gemma4Config` subclass registered for `model_type=gemma4_unified`) shadows
transformers 5.12.1's native `Gemma4UnifiedConfig`, so the encoder-free 12B got the SigLIP
`Gemma4VisionConfig` and died at init on `model_patch_size`. This is the v0.5.16-era "config-alias boot
crash" the 3090 team reported; it was masked on this rig because patch 072's vendored config carried the
attribute until v0.5.16 dropped 072, and gemma4-12b was not in the v0.5.16 validation set (its 5/5 baseline
is from v0.5.15). 098 prefers the native class and keeps the alias only for older transformers, and sets
`lm_head_is_tied` in `Gemma4UnifiedForConditionalGeneration.__init__` — v0.5.18's shared `gemma4_mm.forward`
reads it, but only the parent `__init__` (which the unified class replaces) assigned it, so the 12B died at
its first forward once init succeeded.

## 3090 v0.5.17-flip findings, audited against this stack

The 3090 team's v0.5.17 notes (2026-08-16/18, kept in git history) named four hazards; each was checked here:

- **CT-presharded MoE silent corruption.** v0.5.18's `_load_w2`/`_load_w13` derive the shard from the
  *buffer* (`expert_data.shape[shard_dim]`) and narrow the loaded weight. Every CT/FP8 MoE checkpoint we
  serve stores full-width experts (North `down_proj [2048, 768]`, Laguna `[2048, 512]`, Gemma-4-26B FP8
  `[128, 2816, 704]`, Nemotron-Omni `[2688, 1856]`), so the narrow is exact — the presharded half-load
  path does not apply. Quality on north-mini/laguna is still gated by the fleet run below.
- **`--mm-feature-transport` default → `cuda_ipc`.** On this rig `auto` resolves to `cpu` (serve logs:
  `mm_feature_transport': 'cpu'`; no `pidfd`/`cuda_ipc` in any log; `ptrace_scope=1`). No preset change.
- **Registration double-register hazard.** None of the series adds `EntryClass` registrations;
  `ModelRegistry` imports clean (242 architectures). Added as a preflight habit: `python -c "from
  sglang.srt.models.registry import ModelRegistry"` before booting.
- **Read-only resolved `ServerArgs`.** Confirmed on v0.5.18 (plain assignment raises); the sanctioned
  pre-publish mutation is `server_args._late_resolution(source, **fields)` (v0.5.17 named it
  `override`). `docker/secure-launch.py` now routes its credential/policy fields through a
  version-tolerant resolver (verified on v0.5.18; the image itself was not rebuilt here).
- The `NS("<namespace>")` field lint (`test_server_args_namespaces.py`) passes on the patched tree.
